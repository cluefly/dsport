# DSport

在一加 / ColorOS 上读取计步传感器。送给系统和微信的 `step_counter` 是当天步数，每天 0 点从 0 开始。步数检测和厂商分钟计步只显示，不修改。

模块跑在 [Vector](https://github.com/JingMatrix/Vector) 里，安装包是 APatch 模块。

## 行为

通用页显示这台手机自己的原始读数。系统计步服务和微信进程里的 `step_counter` 被换成当天步数：当天硬件步数加上已计入的步数。

- 真实步数来自开机后的累计计数，只有重启手机才会归零。0 点不把计数器清零，而是用 0 点前最后一次读数当作当天起点，所以 0 点之后新走的步仍算在今天。
- 当天之内只增加，不减少。负数直接拒绝。0 点和通用页的强制重置会把当天自动累加清零，这是仅有的两处清零。
- 目标低于已经计入的步数时，目标抬到已计入的数字，今天已加上的步数保留。
- 微信记下上次的 `step_counter`，下次用新值减旧值。真实步数仍会送出。一旦真实步数增加，自动累加立刻暂停，直到连续 1 分钟没有新的真实步数再恢复。恢复后，每分钟、每 5 分钟仍按真实步数和自动累加的合计限制：每分钟合计默认是微信每分钟上限减 10（微信为 300 时是 290），每 5 分钟合计是微信的上限（例如 1500）。到达该 5 分钟上限时微信会丢掉这一截，所以自动累加停在它减 1。
- 每天自动累加的步数到达上限后不再加。默认上限是 48000，只算自动累加的总和，不含真实步数，可以在通用页修改。到第二天 0 点，自动累加从 0 再开始，真实步数按新的一天继续算。通用页的「强制重置自动累加」把自动累加清零，并把送出值设为当前真实步数加 0。之后真实步数增加，送出值跟着增加。目标、开关和上限保留。
- 开关打开时，输入的是这一天要计入的目标。开关关闭再保存时，输入的是在已计入步数上再增加的数量。

微信页读取主用户的微信运动配置（`SportKv`）。覆盖通用页时，每分钟写入服务端每分钟减 10，每 5 分钟写入服务端上限。通用页用和微信页相同的行显示这两个合计上限，以及自动累加实际停下的数字。手改这两个数时，不能大于微信页读到的折成每分钟和 5 分钟上限，超出的输入会放弃并提示。这需要 APatch 授予本应用 root。

## 作用域

在 Vector 里启用本模块，作用域包含：

- `com.oplus.exsystemservice`
- `com.oplus.healthservice`
- `com.tencent.mm`

`exsystemservice` 和 `healthservice` 负责按上限释放步数，并在 0 点写下当天基线。微信使用同一份当天步数。本应用自己的界面不挂钩，用来看原始传感器。

配置接口 `dev.dsport.module.config` 只接受本应用、root、shell、系统 uid，以及上面三个包。其他应用不能读写目标步数或状态。

## 构建

需要本机的 JDK 17 和 Android SDK 34，默认路径：

- `$HOME/.local/jdk/temurin-17`
- `$HOME/.local/android-sdk`，其中要有 `platforms/android-34` 和 `build-tools/34.0.0`

```bash
./build.sh
```

脚本会先跑 `StepMathTest`，再生成：

- `dist/dsport.apk`
- `dist/dsport-0.2.zip`（APatch 模块，内含 apk）

`dist/` 不入库。调试签名在本机 `$HOME/.local/android-sdk/dsport-debug.keystore`，第一次构建时生成。

## 安装

把 `dist/dsport-0.2.zip` 装进 APatch。模块脚本会执行 `pm install -r -g`，并授予活动识别权限。装好后在 Vector 里确认模块已启用、作用域如上。

已经装过旧版时，直接覆盖安装这份 zip。开机脚本会再用模块目录里的 apk 装一次。改完钩子后，重新打开微信；计步服务如果还在用旧代码，重启一次 `com.oplus.exsystemservice` 或重启手机。
